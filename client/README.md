# Client

The front end of the lab: a medical information desk. Inquiries from clinicians arrive here, through a public contact form or typed in by desk staff, are handed to an agent, and come back with a reply, the passages of the drug label it relied on, and any adverse event case it opened. People review those cases here too.

It is a React app and a small Node server that the app talks to. Desk staff sign in through the lab's [identity provider](../platform/identity/README.md); the contact form and the lab explorer have nobody signed in, and the server calls agents for them, and the retrieval service for the lab explorer, as their own clients there. All data in it is synthetic.

Every command on this page is run from the root of the repository.

## Run it

```bash
platform/identity/setup.sh
docker compose up -d --build --wait
```

Then open <http://localhost:3000>, by that name and not `127.0.0.1`: the identity provider sends the browser back to `localhost`, and the session cookie belongs to it. Sign in as one of the four people: `dana.desk` (who runs the intake agents and the orchestrator), `morgan.medinfo` (who also runs the label expert), `riley.reviewer` (who reads and decides cases) or `avery.auditor` (who reads cases, and may read every run's trace on the trace routes); each person's password is their username (the people are synthetic, the lab is local, and they are typed by hand), which the first command writes to `platform/identity/.env`. What each person sees is set by the scopes their role is granted; see [what each person sees](#what-each-person-sees).

That starts the client together with the [agents](../agents/README.md), the [case system](../tools/case-system/README.md), the [identity provider](../platform/identity/README.md), and the search engine and retrieval service of [knowledge](../knowledge/README.md), on one network. All are published on this machine only. The agents need the model server, so [set that up](../model/README.md) first.

```bash
docker compose down
```

stops them and keeps the inquiries, the cases and the label index. Add `-v` to delete all three. To delete only the inquiries and the cases, and keep the label index, run [`reset-demo-data.sh`](../reset-demo-data.sh): it asks first, then starts the client and the case system again with empty stores.

## What each person sees

`GET /api/session` gives the person signed in and what they may do: `{ user: { name, username, roles }, may: { agents, read_cases, decide_cases, read_traces } }`. `may` comes only from the scopes the identity provider granted at sign-in; the role names are returned, never compared.

| Granted | The session may | The app shows |
|---|---|---|
| An agent's `scope` (`agents:intake`, `agents:expert`, `agents:orchestrator`) | Read the desk's inbox: every inquiry and its runs. Send an inquiry, or a new run of any inquiry, to that agent | Inbox and Log an inquiry, for `agents:orchestrator`; Ask the label, for `agents:expert` |
| `cases:read` | Read the case list and a case, and an inquiry and its runs by its id | Cases |
| `cases:review` | Decide a case | The decision controls on a case |
| `traces:read` | Read every person's runs with their steps, on the trace routes | Nothing: the desk has no screen for traces. The [lab explorer](#the-lab-explorer) shows every run to anyone |
| None of these | Nothing that reaches an agent, the case system, an inquiry or a trace; `/api/session`, `/api/status`, `/api/samples`, an empty `/api/agents` and an empty list of inquiries still answer | A sentence saying the account has nothing to do here |

`/api/agents` lists only the agents the session may run. A call for anything else is answered 403 `not_allowed` before the identity provider or the target is asked. The inbox is the desk's, not one person's: the list gives every inquiry to a session that may run at least one agent, and an inquiry by its id is read by a session that may run an agent or read cases. To any other session an inquiry is answered exactly as one that does not exist (404 `inquiry_not_found`). What the lab explorer entered or ran is not part of the desk: the desk's inquiry routes do not show it. An inquiry's `entered_by` and a run's `started_by` name the member of staff, or `Contact form` or `Lab explorer` for the two clients nobody signs in to (`Lab explorer` only on the trace routes and in the explorer).

On the desk's API a run's steps are given only on the trace routes. Every other `/api` route gives a run with the agent's response less its `steps`; the [lab explorer](#the-lab-explorer) gives them too.

The steps arrive in the agent's response and are stored by the client with the rest of it. `traces:read` is a permission on reading them from that store; there is no separate store of traces.

## The lab explorer

A separate tool for whoever runs the lab on their own machine, at <http://localhost:3000/lab>. It shows what is under the hood: the state of each piece, every configured agent, the prepared inquiries, every inquiry and run with its steps, what the label index holds and the evaluation harness's runs. It runs a message, prepared or written there, or an inquiry already received, through any agent, and runs a label search the way the label expert does: find the label, then search it.

It needs no sign-in. The client is published on this machine only (`127.0.0.1:3000` in [`compose.yaml`](compose.yaml)), so only someone at this machine can reach it. Who may read what is a rule of the desk, the product that desk staff sign in to; it does not apply to the explorer. A run started from the explorer is sent to the agent with a token the server gets by client credentials as the client `lab-explorer`, for that agent's scope alone, and is recorded as started by `Lab explorer`; the agent checks that token as it checks any other. What the explorer enters or runs stays out of the desk's inbox: the desk's inquiry routes do not show it, so a run from the explorer on a desk inquiry does not replace the reply the desk shows. Cases are not kept apart: the case system is the lab's one record of cases, so a run from the explorer that reports a side effect opens a case that the desk's review queue shows, and that case's history says it was opened for the lab explorer. [`reset-demo-data.sh`](../reset-demo-data.sh) clears the cases and the inquiries. A label search from the explorer is sent to the retrieval service with a token the server gets by client credentials as the client `lab-explorer`, for `labels:search` alone, which the service checks as it checks the label expert's; it records nothing, and the medicine, the question and the passages are not logged. What the index holds is read from the search engine directly, with no token: the engine has no sign-in and publishes no port (see [knowledge](../knowledge/README.md), "Not present"). The evaluation harness's data folder is mounted into the client's container read-only, at `/evaluation-data`; the server reads `scores.json`, `run.json` and `results.jsonl` there with schemas of its own that name only the fields it uses, and imports no code of the harness. Its routes, under `/lab/api`, are in the table above: they read no cookie, answer a method a route does not take with 405 `method_not_allowed` (`POST /lab/api/runs` and `POST /lab/api/knowledge/search` are the two routes that take POST), and an unknown path with 404 `not_found`, in the same JSON shape as `/api`. Any other path under `/lab` is the app's page, as every path outside `/api`, `/auth`, `/ping`, `/lab/api` and `/contact/api` is.

## The contact form

The way in for a clinician, with no sign-in: `POST /contact/api/messages` with their name, their role, how to reach them and their message. Each of the first three is at most 200 characters, and the message at most 10,000, as on `POST /api/inquiries`; a field that is missing, empty or too long is 400 `bad_request` naming it. Any other method is 405.

The message is stored as an inquiry from `<name>, <role>, <contact>`, entered by `Contact form`, and the sender is answered 202 with when it was received, and nothing else: no id, no run, no outcome. One run of it by the agent `orchestrator` is then started by `Contact form`, sent with a token the server gets by client credentials as the client `contact-form`, for the orchestrator's scope alone. If that token cannot be got, or with too little life for the wait for the orchestrator, or no agent `orchestrator` is configured, the run is recorded as failed with the reason, and the desk shows it in its inbox like any other.

## Always true

1. A message gets its identifier and receipt time once; sending it again reuses both.
2. Sending answers at once, and a run always ends as finished or failed, including after a restart.
3. An agent's answer outside the contract is a failed run with the reason.
4. Only a sign-in the provider vouched for creates a session, and only in the browser that started it.
5. Every call to an agent or the case system carries a token got for that target alone, with enough life left. A session's is got by a refresh first; refreshes of one session never overlap, and each uses the newest refresh token; a failed one ends the session. The contact form's and the lab explorer's are got by client credentials, each as its own client.
6. The reviewer of a case is whoever is signed in, never a name the browser sends.
7. No token reaches the browser.
8. Signing out removes the session and revokes the refresh token; a failed revocation does not stop it.
9. A POST from another site is refused.
10. What a session may do comes from the scopes it was granted at sign-in: which agents it may run, whether it may read cases, whether it may decide one, whether it may read traces. A call for anything else is answered 403 before the identity provider or the target is asked.
11. The inbox is the desk's: an inquiry and its runs are read by any session that may run an agent or read cases, and a run is started on any inquiry by a session that may run that agent. To a session that may do neither, an inquiry is answered as an unknown one is. An inquiry the lab explorer entered, and a run it started, are not shown on the desk's inquiry routes.
12. On the desk's API a run's steps leave the server only on the trace routes, and only to a session granted `traces:read`. Any other session is answered 403 there before the store is read, so the answer says nothing about whether a run exists. Every other `/api` route returns a run without its steps, to anyone. The trace routes cover every person's runs; an id that names no run is 404.
13. The lab explorer's routes, under `/lab/api`, need no session. They give the pieces' state, the agents, the prepared inquiries, every inquiry and run with its steps, what the label index holds, and each evaluation run's figures (identifiers, verdicts, counts and shares, never a question, answer, reply or reason) to anyone who can reach the server. An evaluation run is named by an id found on disk; any other is 404. `POST /lab/api/runs` runs a message through any agent, and `POST /lab/api/knowledge/search` runs a label search through the retrieval service, each as the lab explorer's own client with a token for that target's scope alone; the search returns the service's hits, and a token or service failure is answered 502 with its reason. They decide no case and change no inquiry. Every route but those two takes GET only. The server is published on this machine only.
14. A message sent through the contact form is stored and handed to the orchestrator as the contact form's own client. The sender is told when it was received and nothing else, whatever the run does. A message that is refused is not stored.

The server's tests in `test/` are one per item, named by its number, with one probe that the built app is served and that any other path is its page. The server's tests run through the server with scripted agents, a scripted case system, an identity provider whose refresh is a function, a function in place of getting a token by client credentials, values in place of the retrieval service and the search engine, and a folder of invented evaluation files, with three exceptions: invariant 4 and those beside it in `auth.test.ts` use the stand-in provider, invariant 5's two calls arriving together run on the token function in `src/tokens.ts`, and invariant 2's restart runs on the store.

## How it is put together

```
browser ── React app ──> client server ──> agents          POST /invocations      bearer token
   │      session cookie      │──────────> case system     review server          bearer token
   │                          │──────────> identity        discovery, token (refresh, client credentials), keys
   │                          │──────────> retrieval, search engine, model servers   health checks   nothing
   │                          │──────────> retrieval         label search, for the lab explorer   bearer token
   │                          │──────────> search engine     the index's alias, count, mapping    nothing
   └──── sign-in pages ──────────────────> identity        http://localhost:8090
                              └─ SQLite on a volume: inquiries and runs
```

- **The server is where a message is received.** It gives the message its identifier and receipt time once, before any agent sees it. Sending the message again reuses both, which is what lets the case system open one case per message.
- **A run does not block the page.** Sending answers at once with the run marked as working; the app asks again until it has finished or failed.
- **What an agent returns is checked against the contract** in [`shared/agent-contract.ts`](../shared/agent-contract.ts). An answer outside it is shown as a failed run with the reason.
- **The app never talks to an agent or the case system directly.** Only the server does, so the page holds no addresses or credentials.
- **Signing in is the server's job.** It runs the Authorization Code flow with PKCE against the identity provider, validates the ID token (signature against the provider's published keys, issuer, audience, nonce, expiry), and keeps the user and their tokens in memory under a random session identifier. The browser holds only that identifier, in an `HttpOnly`, `SameSite=Lax` cookie. Sessions end when the server restarts.
- **Sign-in asks for the scopes the targets need:** `openid`, each distinct agent `scope` configured, `cases:read` and `cases:review`, and `traces:read`, which no target is sent: the server checks it on the session. The provider leaves out any the person's role does not grant and still signs them in; the scopes it granted, read from the token response's `scope`, are kept on the session. The access token from sign-in is sent to nobody.
- **Every call to an agent or the case system carries a token got for that target alone,** as `Authorization: Bearer`. A target is a scope: the agent's `scope`, `cases:read` for reading cases, `cases:review` for a decision. The session keeps one token per scope. Before calling an agent the kept token must have as long left as the server waits for that agent (its `wait_seconds`); before calling the case system, 30 seconds. With less, or none, the server refreshes with `scope=openid <that scope>` and keeps the result under that scope.
- **The contact form and the lab explorer call agents as their own clients.** Nobody is signed in to either, so for each run they start the server gets a new token by client credentials at the token endpoint named in the identity provider's discovery document, as the client `contact-form` or `lab-explorer` with its own secret, asking for the agent's `scope` alone. The inquiry and its run are stored before the token is asked for, so the answer does not wait on the identity provider. A token that cannot be got, or that has less life left than the wait for that agent, is not sent: the run is recorded as failed with the reason. A label search from the lab explorer gets its own token the same way, for `labels:search` alone, before the first call; one that cannot be got is answered 502 and nothing is sent.
- **Refreshes of one session run one at a time, in the order asked.** Each uses the newest refresh token the provider returned, and looks again for a kept token when its turn comes, so two calls for the same target share one refresh. If a refresh fails, the session ends, the request answers 401, nothing is sent, and the user signs in again. If it succeeds with a token that lacks the scope asked for, the request answers 403 `not_allowed` and the session goes on. Health checks carry no token. The agents and the case system each check the token and refuse a call without a valid one.
- **The reviewer of a case is whoever is signed in.** The server forwards a decision as `{ decision, note? }` with the token got for `cases:review` and no reviewer field; the case system takes the reviewer's name and subject from the token. A decision that names its own reviewer is refused here with 400, and one from a session not granted `cases:review` with 403. The case system refuses both behind it too, and its answers are passed back unchanged.
- **No token reaches the browser.** No response body and no header carries an access, refresh or ID token. `Set-Cookie` carries the session identifier and the sign-in binding, neither of them a token.
- **Signing out** removes the session, clears the cookie, revokes the refresh token at the revocation endpoint set by `OIDC_REVOCATION_ENDPOINT` (unless that is `none`), and sends the browser to the provider's end-session URL with `client_id` and the post-logout redirect URI, and no token. If the revocation fails, sign-out still ends the session here and the failure is logged.
- **Only the browser that started a sign-in can complete it.** `/auth/login` sets a second cookie, `desk_signin` (`HttpOnly`, `SameSite=Lax`, `Path=/auth`, 10 minutes), holding a random value kept with the pending sign-in; the callback is refused without it or with another sign-in's, and clears it.
- **A POST from a page on another site is refused,** by its `Origin` header.

## Settings

Set in [`compose.yaml`](compose.yaml).

| Setting | Meaning |
|---|---|
| `AGENTS` | The agents an inquiry can be sent to: a JSON list of `{ id, name, description, scope, url, wait_seconds? }`, where `scope` (`agents:intake`, `agents:expert` or `agents:orchestrator`) is what a token sent to the agent must hold and what a person must be granted to run it, and `wait_seconds` (a whole number from 30 to 295, 180 when absent) is how long the server waits for that agent's answer. 295 is the most because Node's `fetch` stops waiting at 300 s. Four are configured: both intake agents, the label expert, and the orchestrator, which is waited for 295 s |
| `CASE_REVIEW_URL` | Where the case system's review server is |
| `CLIENT_DB_PATH` | The SQLite file for inquiries and runs |
| `WEB_ROOT` | The folder holding the built app |
| `OIDC_DISCOVERY_URL` | Where the server fetches the identity provider's discovery document: `http://identity:8080/realms/lab/.well-known/openid-configuration` |
| `OIDC_ISSUER` | The issuer that document and every ID token must name, exactly: `http://localhost:8090/realms/lab` |
| `OIDC_CLIENT_ID` | `desk` |
| `OIDC_CLIENT_SECRET` | The desk client's secret: `IDENTITY_DESK_CLIENT_SECRET` from `platform/identity/.env` |
| `CONTACT_FORM_CLIENT_SECRET` | The secret of the client `contact-form` at the identity provider, which the contact form's runs are sent as |
| `LAB_EXPLORER_CLIENT_SECRET` | The secret of the client `lab-explorer` at the identity provider, which the lab explorer's runs are sent as |
| `OIDC_REDIRECT_URI` | `http://localhost:3000/auth/callback` |
| `OIDC_POST_LOGOUT_REDIRECT_URI` | `http://localhost:3000/` |
| `OIDC_REVOCATION_ENDPOINT` | Where the refresh token is revoked at sign-out: `http://identity:8080/realms/lab/protocol/openid-connect/revoke`, or `none` for a provider without one. A setting, not taken from the discovery document, because Keycloak names this one endpoint at the browser's address (`localhost:8090`) even when its document is fetched from inside the network, and the server cannot reach that address |
| `APP_ORIGIN` | The origin the app is served from: `http://localhost:3000` |
| `ROLES_CLAIM` | The ID-token claim that lists the user's roles, returned by `GET /api/session`: `roles` |
| `RETRIEVAL_URL` | Where the status checks the retrieval service, and where the lab explorer's label search calls its MCP endpoint (`/mcp`): `http://knowledge:8000`. Optional |
| `SEARCH_URL` | Where the status checks the search engine, and where the lab explorer reads what the label index holds: `http://search:9200`. Optional |
| `EVALUATION_DATA_DIR` | Where the lab explorer reads the evaluation harness's runs: `/evaluation-data`, where `compose.yaml` mounts `evaluation/data` read-only. Optional: when it is not set, the explorer says no run can be read |
| `MODEL_BASE_URL`, `MODEL_EMBED_BASE_URL`, `MODEL_RERANK_BASE_URL` | The chat, embedding and reranker model servers' base URLs, each ending in `/v1`, from `model/.env`, which the root `compose.yaml` reads for this file. The status checks `/health` at each less its `/v1`. Optional. `MODEL_API_KEY` is not passed in |

The case system's two scopes, `cases:read` and `cases:review`, and the client ids `contact-form` and `lab-explorer` are fixed in the code. Every setting is required except the five the status checks by health and `EVALUATION_DATA_DIR`; the server stops at start-up naming any required one that is missing. One of those five that is absent or empty is reported `not_configured`, and the lab explorer's knowledge routes answer 503 `not_configured` naming `SEARCH_URL` or `RETRIEVAL_URL`; one that is not an `http` or `https` URL stops the server at start-up, naming it. The identity provider is not asked anything until someone signs in, a message arrives through the contact form, or the lab explorer starts a run or a label search, so the server starts, and answers `/ping` and the app, while it is down.

## Known limits

- **Sessions live in the server's memory.** A restart signs everyone out. Otherwise a session is removed only by signing out, or when a call cannot get its token: a failed refresh, a session with no refresh token, or a refreshed token with less life than the call needs.
- **What a session may do is fixed at sign-in.** A change to a person's role takes effect when they sign in again.
- **The cookie is not marked `Secure`,** because the lab is served over plain HTTP on this machine.
- **A run that is in progress when the server stops is marked as failed** when it starts again. The agent may still have acted.
- **The inbox reads each listed inquiry whose latest run has finished once more, in full,** because the list gives a run's state and case numbers but not its outcome or what it did to each case. Up to 100 requests open the inbox the first time.
- **The desk shows only an inquiry's latest run,** and has no way to send an inquiry to an agent again. The lab explorer can, and shows every run of an inquiry.
- **A case's original message is the message of its first version.** The messages its follow-ups were recorded from are named in its history by their sender, not shown.
- **The contact form tells the sender only that the message was received, and when.** It shows nothing of how the message is handled or of the reply; the desk's draft reply is copied out to be sent.
- **A run from the lab explorer opens real cases.** A run that reports a side effect has opened a case in the case system, which the desk's review queue shows; its history says it was opened for the lab explorer. [`reset-demo-data.sh`](../reset-demo-data.sh) clears the cases and the inquiries.
- **"All agents" on the lab explorer's Scenarios posts one run at a time.** A refused post stops the ones after it; the runs already started go on.
- **An edited draft is not saved.** The edit is held in the page's memory for that run, kept while the person opens other screens and lost when the page is reloaded; nothing of it reaches the server. The reply is copied out to be sent.
- **The inbox search covers the 100 newest inquiries,** the most the server lists. When there are more, the search says so; an older inquiry is not found.
- **A piece the status reports up answers its health check, and no more.** A model server's `/health` needs no key, so an up model server says nothing of whether it accepts the agents' key; the retrieval service's `/ping` says nothing of whether the label index exists.
- **The React app has no tests.** The repository check typechecks, lints and builds it.
- **The lab explorer's label search searches the first label found.** `find_labels` lists the labels newest first; the others found are listed, not searched, and the search asks for the service's default number of passages.
- **The lab explorer shows an evaluation run's figures, not a comparison of two runs.** `evaluation/compare.sh` makes that. A benchmark run that has not been scored (no `scores.json`) is listed among the files not read.
